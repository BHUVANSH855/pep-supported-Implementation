# PEP 425 — Compatibility Tags for Built Distributions

**URL:** https://peps.python.org/pep-0425/
**Status:** Final
**Relevance:** High — solves implementation compatibility for wheels,
not for sdists

## What it does

Defines the wheel filename tag system:

```
{distribution}-{version}-{python tag}-{abi tag}-{platform tag}.whl
```

The Python tag encodes implementation and version:

| Tag | Meaning |
|---|---|
| `cp313` | CPython 3.13 |
| `pp310` | PyPy 3.10 |
| `py3` | Generic Python 3 (any implementation) |

pip uses these tags to determine whether a wheel is compatible
with the running interpreter before downloading.

## Critical architectural distinction

PEP 425 explicitly states that compatibility tags do NOT go into
the wheel METADATA file because tags describe a particular built
artifact, not the project/distribution as a whole.

| Layer | Mechanism |
|---|---|
| Artifact compatibility | PEP 425 wheel tags |
| Release compatibility | Core Metadata (Requires-Python) |

## What PEP 425 solves

Implementation compatibility for built distributions (wheels) is
fully solved. pip correctly selects `cp313` over `pp310` wheels.

## What PEP 425 does NOT solve

Implementation compatibility for source distributions (sdists).
An sdist filename carries no implementation tag. When pip falls back
to an sdist, it has no pre-build signal about implementation
compatibility from the artifact itself.

## The packaging.tags issue

Issue #311 on pypa/packaging confirms that `*-none-any` wheels for
non-`py*` interpreter tags were historically broken. `pp3-none-any`
was added as a special case in packaging 21.3. `cp3-none-any` is
not currently generated by `packaging.tags`.

Source: https://github.com/pypa/packaging/issues/311

## Implication for this proposal

`Requires-Implementation` is NOT a replacement for PEP 425.
Wheel tag selection remains unchanged. The proposal addresses
a different semantic layer: the release/project level.
